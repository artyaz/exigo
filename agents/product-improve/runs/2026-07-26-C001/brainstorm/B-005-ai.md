## Ideas

### I-001-029: Tutor route bypasses resolveAiProvider — BYOK broken for tutor

- Description: The tutor route (`src/app/api/learn/tutor/route.ts:84,133`) uses `getEnvGeminiClient()` and `getEnvGeminiModel()` directly, constructing a raw `GoogleGenAI` instance. Every other learn route (teach:151, clarify:130) and all generate routes use `resolveAiProvider(convex)`, which honours user BYOK settings. The tutor needs tool-calling (FunctionDeclaration), which the `AiProvider` interface doesn't expose — but the fix is to extend the interface or pass tool config through `AiGenerateRequest`, not to bypass the resolver entirely.
- North-star improvement: Makes the provider decision consistent (one place, readable) and correct for BYOK users.
- Riskiest assumption: The `AiProvider` interface can be extended with an optional `tools` field without destabilising the OpenAI adapter (which would need a different tool-call wire format).
- Warrant: The comment in `geminiEnv.ts:6-8` explicitly says "Prefer resolveAiProvider when BYOK/settings apply; use these only for the default-env path until F-W7-002 lands fully." The tutor is a primary user-facing surface; BYOK users silently get the wrong provider.
- Effort: M

### I-001-030: Tutor route hand-rolls SSE Response instead of using sseResponse helper

- Description: `src/app/api/learn/tutor/route.ts:323-329` manually constructs `new Response(stream, { headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache", Connection: "keep-alive" } })`. The shared `sseResponse()` helper in `src/lib/sse.ts:47-49` adds `X-Accel-Buffering: no` and `no-transform` to Cache-Control — both important for proxies/CDNs. The tutor is the only streaming route that doesn't use the helper.
- North-star improvement: Consistent wire behaviour across all SSE routes; one less place to diverge when headers change.
- Riskiest assumption: None significant — this is a mechanical swap with no behavioural risk.
- Warrant: The `sse.ts` module header (line 5-10) documents the majority dialect and states product routes should use `sseData`/`sseDelta`/`sseDone`/`sseError`. The tutor already uses `sseData` for framing but misses the response wrapper.
- Effort: S

### I-001-031: 429 retry logic exists only in tests/generate — learn and generate routes are unprotected

- Description: `src/app/api/tests/generate/route.ts:77-108` implements a 3-attempt retry loop with exponential backoff for HTTP 429. No other AI route (teach, clarify, tutor, atlas, embed, exercise, lesson, lesson-exercises, open) has any retry. A single rate-limit hit from Gemini or a user's custom endpoint silently fails the stream. The retry logic should be extracted into a shared `streamWithRetry(provider, req, opts)` helper in `src/server/ai/` and adopted by all streaming routes.
- North-star improvement: Correct behaviour under transient rate limits; shorter routes once the pattern is centralised.
- Riskiest assumption: Retry is safe for idempotent generation calls but could double-emit side effects (e.g., saving messages) if the retry wraps too much; the helper must wrap only the provider.stream() call.
- Warrant: Gemini's free tier and many OpenAI-compatible endpoints return 429 frequently under load. Users see "Teaching failed" with no recovery. The existing retry in tests/generate proves the pattern works.
- Effort: M

### I-001-032: /api/generate/* routes have zero PostHog AI observability

- Description: None of the six generate routes (atlas, embed, exercise, lesson, lesson-exercises, open) call `captureAiGenerationEvent`. These routes make real AI calls (some expensive — atlas fans out ~75 nodes, lesson-exercises runs parallel embed builds) but produce no `$ai_generation` events. Cost tracking, latency percentiles, and model-quality dashboards are blind to this traffic. Each route already has `provider` resolved; adding a capture call around the generation is mechanical.
- North-star improvement: Correct observability coverage; enables data-driven model/cost decisions.
- Riskiest assumption: The non-streaming routes (embed, exercise, open) return a single `AiResult` — capturing latency and token metadata is straightforward, but atlas's multi-node fan-out needs an aggregate event shape to avoid event spam.
- Warrant: `shared/posthogAiObservability.ts` was built for exactly this. The learn routes and tests routes all emit events; the generate routes are the only gap. PostHog AI dashboards currently undercount real usage.
- Effort: M

### I-001-033: Tutor error handling lacks structured logging and uses inconsistent SSE error shape

- Description: The tutor route's catch block (`route.ts:316-318`) does `send("error", { error: "Tutor request failed" })` then `controller.close()`. It doesn't call `logError` from `otlpLogger`, doesn't include `requestId`, and doesn't use `enqueueSseError`. Compare with teach (`route.ts:246-254`) and clarify (`route.ts:172-180`) which both call `logError` with structured attributes and use `enqueueSseError`. The tutor also lacks `requestId` creation entirely (no `createRequestId(req.headers)` call).
- North-star improvement: Consistent error observability; errors are traceable in OTLP and the client sees the same SSE error dialect everywhere.
- Riskiest assumption: Adding `requestId` and `logError` to the tutor is purely additive and cannot break the stream.
- Warrant: Without structured logs, tutor failures are invisible in production debugging. The `otlpLogger` pattern is already established in every other learn route.
- Effort: S

### I-001-034: PostHog event shape diverges between routes — tutor passes synthetic response, teach passes raw chunk

- Description: In `teach/route.ts:188`, `response: lastChunk` passes the raw vendor chunk (enabling token/status extraction via `extractTokenAndStatusMetadata`). In `tutor/route.ts:213,237`, `response: { text: fullResponse }` passes a synthetic object that has no `usageMetadata` or `sdkHttpResponse`, so token counts and HTTP status are always 0/undefined. The tutor also omits `stream: true` and `timeToFirstTokenSeconds`. This makes cross-route analytics inconsistent — tutor generations appear to use 0 tokens.
- North-star improvement: Correct, comparable observability data across all AI surfaces.
- Riskiest assumption: The tutor's non-streaming initial call (`generateContent`) does return `usageMetadata` on the response object; capturing it requires holding a reference to `initialResponse` rather than discarding it.
- Warrant: `posthogAiObservability.ts:110-138` already extracts `usageMetadata` and `sdkHttpResponse` — the data is available but the tutor throws it away. Token cost tracking is a key business metric.
- Effort: S

### I-001-035: geminiEnv.ts is a transitional shim that should be deleted once tutor migrates

- Description: `src/server/ai/geminiEnv.ts` (19 lines) exports `getEnvGeminiClient()` and `getEnvGeminiModel()`. Its own doc comment (line 6-8) says it exists for routes "that still construct GoogleGenAI directly" and to "prefer resolveAiProvider." The only consumer is the tutor route (confirmed by grep: 3 hits, all in tutor). Once I-001-029 lands (tutor uses resolveAiProvider), this file has zero consumers and should be deleted per the "delete > move > rewrite" convention.
- North-star improvement: Shorter codebase, fewer entry points to misuse; the "one provider decision" invariant becomes enforceable by lint.
- Riskiest assumption: No other code path (Convex actions, scripts) imports geminiEnv — grep confirms only the tutor route does.
- Warrant: The file is explicitly labelled transitional. Keeping dead shims invites future routes to bypass the resolver. Deletion is the cleanest enforcement.
- Effort: S

## Patterns observed

1. **Two-tier provider access**: `resolveAiProvider` (BYOK-aware) vs `getEnvGeminiClient` (env-only). The split exists because the `AiProvider` interface lacks tool-calling support. Only the tutor needs tools, so it's the sole holdout.
2. **SSE dialect is well-centralised** in `src/lib/sse.ts` with clear helpers. All routes except tutor use `sseResponse()`. The atlas route intentionally uses NDJSON (different content type) — that's a deliberate design choice, not drift.
3. **PostHog coverage correlates with route age**: older learn routes (teach, clarify) have full observability; newer generate routes shipped without it.
4. **Retry is route-local, not provider-level**: the 429 retry in tests/generate wraps the stream iterator, not the provider. This means it can't be reused without copy-paste.
5. **Error handling has two tiers**: learn routes use `logError` + `enqueueSseError`; the tutor uses a bare `send("error", ...)` with no server-side log.
6. **Convex actions (courseAi.ts, courseTutor.ts) use direct Gemini** — this is the intentional second AI path and is correctly separate from the Next API layer.

## Recommended brainstorm clusters

1. **Provider unification** (I-001-029, I-001-035): Extend `AiProvider` with optional tool support → migrate tutor → delete geminiEnv shim. Single PR, high consistency gain.
2. **Streaming resilience** (I-001-031): Extract `streamWithRetry` into `src/server/ai/retry.ts`, adopt in all streaming routes. Pairs naturally with provider unification.
3. **Observability completeness** (I-001-032, I-001-034): Add PostHog events to generate routes + fix tutor event shape. Can be one PR with a shared `captureFromProvider` helper.
4. **SSE/error consistency** (I-001-030, I-001-033): Mechanical fixes — swap tutor to `sseResponse`, add `logError`/`requestId`. Smallest effort, immediate consistency win.
