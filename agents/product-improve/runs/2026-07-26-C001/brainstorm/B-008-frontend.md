## Ideas

### I-001-050: Remove dead tRPC + Prisma scaffold entirely

- **Description**: The entire tRPC stack (`src/trpc/`, `src/server/api/`, `src/server/db.ts`, `prisma/`) exists solely to power a single demo `LatestPost` component (`src/app/_components/post.tsx`) that is never imported anywhere. The `TRPCReactProvider` wraps every page in `layout.tsx:37`, adding a QueryClient + httpBatchStreamLink round-trip setup on every load for zero user-facing functionality. Deleting the tRPC provider, post router, post component, Prisma schema, and associated dependencies removes ~400 lines of dead code and one unnecessary network-layer provider from the render tree.
- **North-star improvement**: Readable — eliminates a confusing dual data-fetching paradigm; every new contributor currently must ask "do I use Convex or tRPC?"
- **Riskiest assumption**: Some future feature may want a relational SQL escape hatch that Convex cannot serve.
- **Warrant**: The only consumer (`LatestPost`) is unreferenced; Prisma's `dev.db` is a leftover from `create-t3-app`. Convex already handles all production data. Removing dead code is the highest-confidence improvement per Exigo's "delete > move > rewrite" convention.
- **Effort**: S

### I-001-051: Delete orphaned PaddleCheckoutReceiver component

- **Description**: `src/app/PaddleCheckoutReceiver.tsx` (87 lines) exports `PaddleCheckoutReceiver` but is never imported by any file in the codebase. The checkout flow is fully handled by `src/app/checkout/page.tsx`, which independently loads the Paddle SDK and opens the inline checkout. This orphan adds dead weight and misleads readers into thinking there is a second checkout path.
- **North-star improvement**: Clear — removes a false signal about architecture; one checkout path, one file.
- **Riskiest assumption**: An unreleased branch or integration test may reference this component.
- **Warrant**: `grep` confirms zero imports. The component duplicates logic already present in `checkout/page.tsx` (SDK loading, `Initialize`, `Checkout.open`). Deleting it follows "delete > move > rewrite."
- **Effort**: S

### I-001-052: Fix stale metadata description in layout.tsx

- **Description**: `src/app/layout.tsx:10` sets `description: "Generated by create-t3-app"`. This boilerplate string ships to production `<meta>` tags, harming SEO and brand perception. It should read a concise product description (e.g., "AI-powered study spaces for precise, focused learning." — already written in `page.tsx:21`).
- **North-star improvement**: Correct — the app's public-facing metadata should reflect the actual product, not the scaffolding tool.
- **Riskiest assumption**: None significant; this is a one-line string change.
- **Warrant**: The correct copy already exists in the homepage hero. This is a trivial fix with outsized clarity impact for search engines and social previews.
- **Effort**: S

### I-001-053: Consolidate duplicate Paddle SDK initialization logic

- **Description**: Paddle SDK loading and initialization is duplicated between `checkout/page.tsx:71-101` and the dead `PaddleCheckoutReceiver.tsx:55-75`. Even after deleting the orphan, the checkout page's inline logic (script loading, environment detection, `Initialize` + `Checkout.open` orchestration) is ~30 lines of imperative effect code that could be extracted into a small `usePaddleCheckout(transactionId)` hook. This would make the checkout page declarative and testable.
- **North-star improvement**: Readable — a named hook communicates intent; the page component becomes a thin render shell.
- **Riskiest assumption**: Paddle's global `window.Paddle` lifecycle may resist clean hook encapsulation across HMR boundaries.
- **Warrant**: The current effect chain (`isScriptLoaded` → `transactionId` → `isCheckoutOpened`) is a common source of race-condition bugs. A hook centralizes the state machine and can be unit-tested with a mock SDK.
- **Effort**: S

### I-001-054: Standardize page-level auth guard pattern

- **Description**: Auth protection is implemented inconsistently across routes: `spaces/page.tsx` uses `<SignedOut><RedirectToSignIn/></SignedOut>` (line 87-89), `checkout/page.tsx` renders a sign-in prompt inline (line 105-111), `pricing/page.tsx` renders two entirely separate trees via `<SignedOut>` / `<SignedIn>` (lines 386-468), and the course page relies solely on Convex query skipping. A shared `<RequireAuth>` wrapper or a Next.js middleware redirect (Clerk already protects `/spaces` and `/tests` via middleware) would make the pattern consistent and reduce per-page boilerplate.
- **North-star improvement**: Consistent — one mental model for "this page requires auth" across all routes.
- **Riskiest assumption**: The pricing page intentionally shows public content to signed-out users, so a blanket guard won't fit every route.
- **Warrant**: Three different guard styles in five pages increases cognitive load. Clerk middleware already handles `/spaces`; extending it to `/checkout` and `/settings` removes client-side flicker and code.
- **Effort**: M

### I-001-055: Settings page uses runtime-injected CSS instead of Tailwind

- **Description**: `src/app/settings/page.tsx:9-33` defines a 25-line CSS string injected via `document.createElement("style")` at runtime (line 48-52). Every other page uses Tailwind utility classes and the shared design tokens. This creates a maintenance island: the settings UI cannot benefit from token changes, responsive utilities, or the existing `.glass-card`/`.spring-interact` helpers. Migrating to Tailwind classes (or at minimum a co-located `.module.css`) aligns the page with the rest of the app.
- **North-star improvement**: Consistent — one styling approach across all routes; token changes propagate everywhere.
- **Riskiest assumption**: The BEM-style class names may have been chosen to avoid Tailwind's `@apply` limitations in complex selectors.
- **Warrant**: The runtime `<style>` injection is a code smell (FOUC risk, no SSR, CSP concerns). The page is small (193 lines) and the CSS is straightforward to port to utilities referencing existing tokens.
- **Effort**: M

### I-001-056: Reduce token redundancy between exigo-tokens.css and Tailwind theme

- **Description**: `exigo-tokens.css` defines `--font-sans` (line 10) and `globals.css` re-declares the same variable inside `@theme` (line 5). The white-on-black opacity ladder (`--white-90` … `--white-02`) duplicates Tailwind v4's native `white/90` opacity syntax used throughout components (e.g., `text-white/60`, `border-white/10`). The tokens file is valuable for non-Tailwind contexts (exercise runtime), but within the app shell the overlap creates two sources of truth for the same values.
- **North-star improvement**: Short — removing duplicated declarations reduces the surface area a developer must scan to find the canonical value.
- **Riskiest assumption**: The exercise runtime (`src/app/_components/exercises/embed/runtime.ts:91`) depends on these tokens being present as raw CSS variables.
- **Warrant**: The tokens file explicitly states it serves the exercise runtime. Auditing which tokens are actually consumed outside Tailwind utilities would allow pruning unused variables and removing the `@theme` duplication, shrinking the CSS bundle.
- **Effort**: M

## Patterns observed

1. **Convex-first data layer**: All production pages use `useQuery(api.*)` from Convex. tRPC is entirely vestigial (create-t3-app scaffold).
2. **Client-component pages**: Every page is `"use client"` — no React Server Components are leveraged for data fetching or static shell rendering.
3. **Consistent visual language**: `glass-card`, `spring-interact`, `text-primary/secondary/tertiary` utilities are used consistently across spaces, pricing, and checkout.
4. **Framer Motion for transitions**: `AnimatePresence` + `motion.div` used in spaces list, space detail tabs, and course tabs — consistent pattern.
5. **PostHog integrated at provider level**: `ConvexClientProvider.tsx` handles `identify`/`reset`; error boundaries capture exceptions. Good separation.
6. **Clerk dual rendering**: Pricing page renders two full page trees (`SignedIn`/`SignedOut`) rather than conditional sections, doubling the component size.
7. **No shared loading skeleton**: Each page implements its own `<Loader2>` spinner with ad-hoc sizing/color. No reusable `<PageLoader />`.
