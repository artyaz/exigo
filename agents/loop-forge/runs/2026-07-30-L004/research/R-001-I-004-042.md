## Idea echoed
Repo-first triage: run every source-decidable mechanical check first; publish ONE batched contact-sheet of only the residual pixel-only surfaces; browser scrolls/screenshots each section separately. Riskiest assumption: source triage leaves *only* pixel residue and skips no visually-obvious defect.

## Steelman
Publishing is irreversible, so the artifact count is the true cost. Contrast — the single most frequent defect class — is ~98% automatable and here fully source-derivable: tokens define an exact white-on-black opacity ladder (`--white-30 = rgba(255,255,255,.3)` → 3:1 on black, below AA 4.5:1). Heading order, `alt`, `<label for>`, `<div onclick>` are grep-decidable. So triage legitimately clears the high-volume classes cheaply and reserves the one permanent publish for what genuinely needs a render.

## Toulmin decomposition
- **Claim:** Triage-before-publish leaves only pixel-only residue, so batched single-publish under-reviews nothing material.
- **Grounds:** Contrast 98% automatable; Deque 57%-by-volume skewed by contrast [accessibility.works]. Repo exposes exact contrast tokens (`src/styles/exigo-tokens.css:31-34`) and a focus utility (`globals.css:36-37`).
- **Warrant:** If a defect is deterministically computable from JSX/CSS, a render adds nothing.
- **Backing:** Automated coverage 30–40% of *criteria*; contrast near-perfect [siteimprove; accessibility.works].
- **Qualifier:** Holds only for contrast/structural classes; NOT for focus-order, focus-visibility, meaningful-sequence.
- **Rebuttal:** Keyboard/focus-order automatable at ~2.49%; visible-focus, reading-order, context-color missed by all 13 GDS tools [accessibility.works]. These are render-dependent — but the decision *publishes* exactly this residue, so it does not filter them out.

## Falsification attempt
- **Falsifier proposed:** If a large fraction of real defects are not statically decidable, triage filters out surfaces that needed pixels → systematic under-review.
- **Tested via:** per-criterion automated-coverage data + repo token/focus inspection.
- **Outcome:** Falsifier NOT confirmed for the stated failure mode. 60–70% of defects are indeed render-dependent, but the design *routes those to the publish*, not to the discard bin. Triage only discards a surface when source *settles* it (contrast token below threshold, missing `alt`). Residual claims escalate. The genuine live risk is different: batching. Attention dilution + lost-in-the-middle degrade per-section depth in long multi-section documents [aiskillcerts; arXiv 2510.12251; awesome-skills Architecture.md]. BUT the decision mitigates this precisely — browser screenshots each section separately, giving each surface its own review pass (the documented cure: one focused pass per item). So dilution is bounded if per-section review stays isolated.

## Position-swap reconciliation
- **Supporter:** Contrast — top defect class — is fully source-derivable here; publish count minimised; residue correctly escalated.
- **Detractor:** Source triage cannot prove a *negative* for focus-order/visible-focus; a surface "cleared" as structurally fine may still fail on render.
- **Reconcile (on evidence):** Both hold. Triage is sound for what it *asserts*, unsound if it treats "source-clean" as "surface-clean" for render-only criteria. Fix: triage may CLEAR only classes with high static coverage (contrast, alt, structure); any surface with interactive/focus/sequence relevance must reach the publish regardless of source cleanliness.
